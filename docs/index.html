Clemson Advising MCP Servers

Two read-only Model Context Protocol servers that give an AI advising assistant deterministic access to Clemson's published data — the live class schedule and the College of Business curriculum — so an answer about a section, a requirement, or a conflict is a lookup, never a guess.

Repository Security model Full overview

What the servers provide

An advisor asking “can this student take BUS 3120 next spring?” needs the catalog requirement, the prerequisite chain, and whether a section exists at a time that fits. A language model asked that without tools produces a fluent, plausible, and frequently wrong answer. These servers make each of those facts a deterministic lookup instead.

advising-mcp-schedule · port 8766

Schedule server

The Banner class schedule: section search, meeting times, rooms, seats, conflict checking, alternatives that fit an existing schedule, and authoritative CRN verification. Eleven tools.

advising-mcp-catalog · port 8767

Catalog server

The College of Business curriculum: semester-by-semester degree plans, named requirement rules, General Education, course entries, minors and certificates, and the join between a requirement slot and the sections that fill it. Eleven tools.

Both serve published Clemson data, hold no student records and no credentials beyond their own consumer tokens, and have no write path into any Clemson system. Every caller needs a bearer token; the servers sit on loopback behind a campus reverse proxy that terminates TLS.

Where the information comes from

Source What How often
regssb.sis.clemson.edu Banner's public “Browse Classes” JSON endpoints — the same calls the search page makes. No login, no student data. One paced sweep per live term, daily at 05:00; three tools can also read live for current seat counts
catalog.clemson.edu The published online catalog (Acalog): program pages, course pages, General Education, footnotes. About once a year, when a new catalog year is published — never from the serving host
CuSectionOverview report Room seat counts for 435 rooms — the one input that is not on a public page, exported by hand and named in the security document. Once; not currently returned to any caller

The daily Banner sweep is deliberately gentle with someone else's production system: pages of 500 sections capped at 40, 200–400 ms between requests, one second between terms, at most three attempts per term, and a User-Agent naming this service and repository so the traffic is attributable. A sweep that does not complete is discarded rather than written.

How it is ingested and served

Two independent pipelines feed two independent servers. Neither pipeline runs on a request — collection and serving never share a process.

The class schedule, nightly

Collect
Refresh job, 05:00Asks Banner for its term list, sweeps every live term — currently seven, ~21,000 sections in under three minutes.
→
Rest
One SQLite file per termSections, meetings, instructors, and a “data as of” stamp. Written atomically — a reader never sees a partial snapshot.
→
Serve
Schedule serverOpens the term's file read-only per request. Every answer carries the snapshot's timestamp.

The curriculum catalog, annually

Collect
Catalog rebuildA headless browser renders each program page (the catalog is a JavaScript application); parsers extract plans and rules; a language model extracts the prose requirements of minors and certificates, cached by page content.
→
Rest
catalog.dbPrograms, semester plans, requirement rules, 4,085 courses, General Education, footnotes — with the source page recorded for every row.
→
Serve
Catalog serverReads the database in-process. No request ever runs Python; the pipeline that builds the database is checked against the serving code by a differential test.

The design rule the codebase is organised around: silence must never read as absence. A lookup that found nothing because it did not look says so. Prerequisite eligibility is three-valued (eligible / not eligible / undetermined); a CRN check distinguishes “the snapshot has no such CRN” from “there is no snapshot”; an unreadable catalog is an error, never an empty answer.

A request travels: HTTPS to the campus reverse proxy → loopback HTTP to the server → bearer-token authentication against a per-server registry of hashed tokens → a scope check → the tool's handler, which is a read-only SQLite query (or, for three schedule tools, a live Banner read). One usage-ledger line per call records who called which tool — never the arguments, never the results.

The tools

Twenty-two in all, eleven per server. The repository's test suite compares this list against what the running servers actually serve, so it cannot silently drift.

Schedule server port 8766

Every tool taking a term accepts a code (202608) or a name ("Fall 2026") and defaults to the current registration term.

search-classes

Search sections by subject and/or course number, with instructor, building/room, days, time-of-day, and open-seats filters. Snapshot-backed; refresh: true forces a live Banner read for up-to-the-minute seats.

get-course-details

Details for one course (description, prerequisites, corequisites, restrictions, credits) or one section by CRN. Reads Banner live.

check-conflicts

Which CRNs in a set clash in time, pair by pair; optionally tests candidate CRNs against a fixed set. Sections with no meeting time cannot conflict and are reported as such.

find-alternatives

Sections that fit around the CRNs a student is keeping, with subject, credits, days, time, and seats filters.

find-conflict-free-schedule

Given committed CRNs and candidate CRNs, which candidates can be added with no conflicts — each checked against every fixed CRN and every other candidate.

get-sections-by-crn

What the snapshot records for given CRNs — course, section, credits, every meeting. CRNs with no row come back in not_found, which is authoritative; a term with no snapshot claims nothing.

resolve-crns

The CRN for each course + section pair, for schedule data that carries none. Results align by index; a null means no single match — it never guesses.

get-instructor-classes

Everything each listed instructor teaches in a term — and, with an optional day/window filter, who has a teaching conflict. Not teaching this term is deliberately not the same as free; ambiguous names return candidates rather than a guess.

get-teaching-load

Weekly contact hours and credit hours per instructor, computed server-side — by subject, by instructor list, or both. Untimed sections are reported separately, never folded into a total.

get-schedule-freshness

When a term's snapshot was last ingested — the “data as of” behind every seat count. No Banner load.

list-clemson-terms

Banner's term codes and names, for when no term is known. Live.

list-skills with get-skill-docs

List and fetch the advising guidance documents this server serves to a model — one document, describing which tool to reach for and where the data can mislead.

get-skill-docs

Fetch one skill document in full, by name.

Catalog server port 8767

Program names are the registrar's, exactly as the catalog spells them ("Marketing, BS"); students are pinned to their matriculation catalog year.

list-programs

Every program the catalog can advise on, with the catalog years each exists in — the valid values for every other tool's program argument.

list-catalog-years

The valid catalog-year labels.

get-program-plan

The full semester-by-semester degree plan: required courses, one-of choices, requirement slots, credits, footnotes, and the catalog page it came from.

get-requirement-rules

The named requirement slots — lab science, specialty area, technical, REACH — with explicit courses and credits. Only part of a degree: a course absent here is not absent from the program.

get-gen-ed

Clemson's General Education requirements for a catalog year: six categories with minimum credits, allowed courses, and constraint rules. University-wide.

list-courses

Courses by subject and/or catalog-number range, from the current course inventory — resolves DegreeWorks-style wildcards (MGT @, ACCT 3000:3999) to real codes.

find-course-in-program

Every place a course or subject appears in one program — searching both the semester plan and the requirement rules, which is what makes its “not found” meaningful.

get-course

One course's catalog entry — title, credits, description. An unreadable catalog is an error, never “not found”.

get-program-requirements

What a minor or certificate requires. Partial or misspelled names return candidates to choose from.

find-requirement-sections

The advising join: sections offered this term that fill a named requirement slot and that the student is eligible for. Eligibility is three-valued — undetermined tells the caller to read the actual prerequisite text rather than report the student ineligible.

get-department-rules

A department's recorded slot decisions — faculty-approved additions and denials. Departmental provenance, stated on every response; gated by a scope, so consumers without the grant never see it. Feeds the section search via extra_courses.

get-department-doc

A department's advising-policy document, same provenance and scope gate. Thin documents say they are thin.

list-catalog-skills with get-catalog-skill-docs

List and fetch this server's three shared guidance documents: the department-neutral advising method, catalog usage, and the Pre-Business year. Department policy lives behind get-department-doc.

get-catalog-skill-docs

Fetch one of those documents in full, by name.

Deliberately not tools: anything that writes (there is no write path to any Clemson system), a degree audit over MCP, and anything that takes a student's identity — no tool has a field for one.

Built in TypeScript on Node 22 with Anthropic's official Model Context Protocol SDK (Streamable HTTP transport), reading SQLite in-process via better-sqlite3 — three runtime dependencies, no web framework, no ORM.
